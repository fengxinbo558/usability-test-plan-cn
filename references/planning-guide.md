# 可用性测试计划参考

## 动态样本决策

把每一轮测试视为一次覆盖与学习决策，而不是追逐万能人数。

1. 列出关键旅程、失败代价和必须覆盖的用户/环境单元。
2. 为首轮选择能暴露最大不确定性的组合，并说明招募可行性。
3. 每轮后更新问题台账：问题、严重度、首次/再次出现、触发条件、影响子群、证据位置、反例。
4. 新增问题仍多、高风险条件未覆盖或不同子群出现不同机制时，继续定向招募。
5. 只有当停止条件成立或约束触发时才结束；两者要分别陈述。

“连续轮次未出现新问题”必须限定问题等级和覆盖范围。例如，没有新的高严重度问题，不等于没有低严重度问题；某一角色趋于稳定，不等于其他角色也已稳定。

## 任务卡模板

```markdown
### 任务：<用户目标>
- 情境：
- 起点与测试数据：
- 目标状态：
- 独立完成标准：
- 经提示完成标准：
- 失败/阻断标准：
- 真实操作停止点：
- 观察重点：
- 中性追问：你刚才预期会发生什么？你如何判断已经完成？
```

避免：暴露界面词、讲解正确路径、要求评价主持人提出的方案、用“你是不是觉得……”暗示答案。优先询问最近行为、当下预期与可观察判断。

## 证据与严重度

建议问题记录字段：`issue_id`、产品版本、任务、参与者代号、用户层、原始观察、逐字表达、主持提示、环境异常、影响、恢复路径、严重度、反证、证据位置、待验证项。

严重度可使用四档，但必须附理由：

- 阻断/高风险：关键目标无法完成，或造成安全、资金、隐私、合规、数据损失等严重后果。
- 重大：可完成但需要外部帮助、绕行或高恢复成本。
- 一般：造成明显延迟、困惑或额外步骤，仍可独立恢复。
- 轻微：主要影响流畅度或一致性，不改变任务结果。

数字不自动等于结论。任务时长、完成状态和主观评分可以描述本次样本，但除非另有抽样设计，不推断总体比例或显著差异。

## 中国场景适配清单

- 入口：应用商店、扫码、公众号、企业微信、微信/支付宝小程序或内嵌浏览器。
- 设备：国产安卓系统差异、屏幕尺寸、权限弹窗、系统字体与辅助功能。
- 网络：弱网、跨地区延迟、断线恢复、流量限制。
- 身份与交易：手机号、实名、验证码、支付、发票及最终提交的沙箱/停止点。
- 人群：低数字素养、老年用户、残障用户、城乡与地区服务差异、普通话之外的语言需求。
- 组织软件：采购者、管理员、审批者与一线操作者的权限和目标可能不同。

仅纳入与研究问题有关的维度，避免为了“多样性”收集不必要的敏感信息。

实名或支付任务中，参与者只能接触合成身份、测试卡、测试订单和不会触发真实清算/通知的环境。没有这种环境时，把成功状态定义到最终确认前；生产清算验证必须与参与者研究分离，并经过组织的安全、合规与业务复核。

## 方法参考

- Steve Krug, *Rocket Surgery Made Easy*：轻量可用性测试与主持实践。
- Thomas Tullis & William Albert, *Measuring the User Experience*：可用性指标与量化边界。
- James R. Lewis 与 Jeff Sauro 的可用性度量研究：小样本估计需陈述不确定性。
- ISO 9241-11 的有效性、效率、满意度框架：使用时应核对组织实际采用的标准版本与适用范围。

这些资料提供方法镜头，不构成固定人数公式或合规意见。
